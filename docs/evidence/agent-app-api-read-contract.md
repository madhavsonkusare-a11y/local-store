# Reviewed app API reads

These adapters provide limited private content summaries for six pinned apps. They are read-only; they do not expose a general HTTP proxy, arbitrary method selector, shell, filesystem path or mutation. Live qualification is recorded separately in per-app receipts; code and unit checks alone do not establish app coverage.

| App | Exact upstream reads | Returned fields |
| --- | --- | --- |
| Gitea 1.27.3 | `GET /api/v1/user`, `GET /api/v1/user/repos?limit=20&page=1` | Repository identity, name, description, owner login, private flag |
| WordPress 7.1.0 | XML-RPC `wp.getUsersBlogs`, `wp.getPosts` | Accessible post identity, title, status and bounded content |
| Kanboard 1.2.54 | JSON-RPC `getMe`, `getMyProjects`, `getMyDashboard` | Current-user project and task identities, names and descriptions |
| Immich 3.2.0 | `GET /api/users/me`, fixed metadata `POST /api/search/metadata` | Asset identity, filename, type and dimensions |
| Jellyfin 12.0 | `GET /System/Info`, fixed `GET /Items` | Media identity, name and type |
| Uptime Kuma 2.5.3 | Authenticated `GET /metrics` | Monitor identity, name, type and current status |

The owner connects an app credential explicitly. Credentials use the shared Windows DPAPI store. Connecting grants no agent access. Each client needs a separate expiring read grant for the exact installed app ID. Credential replacement revokes prior grants. Reads check fresh installation, pinned images, selected engine ownership and runtime identity, then check the grant again before releasing a result. Duplicate installed app IDs resolve their catalog identity without changing grant scope.

Replies are bounded to 512 KiB with at most 20 results per list. Dedicated fields for API keys, target URLs, hostnames, filesystem paths, playback links and location metadata are excluded. Allowed text fields preserve their bounded content, including URLs written into a post; those strings are never followed. App text is untrusted data, including private WordPress HTML. The fixture includes explicit malicious instructions and verifies they cannot grant access, enable writes or choose an external URL; audit logs must omit credentials and private text.

WordPress uses fixed read-only XML-RPC because the current local HTTP app does not support normal production application-password authentication. The protected credential is `username:password`. XML parsing refuses DTDs, external/custom entities, unsupported tags, faults, duplicate members and excess depth/nodes. Blog URLs supplied by the app are never followed.

Kanboard accepts a strong user credential or personal API key, not the global JSON-RPC key. Jellyfin uses its current `MediaBrowser` authorization header and validates the protected connection against system info, supporting keys that are not bound to a single user.

Uptime Kuma uses its existing metrics authentication, avoiding a Socket.IO dependency. With API keys enabled, its Basic-auth password is the API key; otherwise it is the owner password. Every read first requires an anonymous 401 response, rejecting disabled authentication before attaching the credential. Its bounded parser reads only `monitor_status`, strips target and tag labels, and maps the pinned status values to down/up/pending/maintenance. Monitoring targets are never contacted by this adapter.

## Reproducing the scoped proofs

Use the selected, ownership-verified Local Store engine. Do not overlap these proofs with another app qualification. The Windows target requires explicit opt-in and runs with one test thread:

```powershell
$env:LOCAL_STORE_RUN_MANAGED_QUALIFICATION = '1'
cargo test --locked --release --features tauri/custom-protocol,mcp-sidecar --test managed_app_api_content -- --ignored --nocapture --test-threads=1
```

When that exact current-source target was already built, invoke the executable printed by Cargo directly with the same trailing test flags to avoid another build. A single test-name filter can isolate an actual remaining issue.

Each proof installs a unique alias of the reviewed app, reuses its existing first-use probe to create synthetic content, then creates its own synthetic access credential. It checks useful private reads, missing/cross-client grants, extra URL/method arguments, write refusal, live revocation, credential replacement, owner disconnect and audit redaction. It uninstalls only its own app and confirms existing containers are unchanged. Uncertain cleanup retains the private fixture for explicit recovery.

Receipts under `docs/evidence/<app>-agent-api-content-2026-10-02.json` are generated by actual runs and bind to the provider, shared permission boundary, test and credential fixture source hashes. Run `python scripts/check-agent-provider-evidence.py --allow-pending` to distinguish current proofs from pending or stale receipts. Source edits require fresh proofs; a passing parser unit test does not count as a live app read.
